## Assets and trust boundaries

The assets are Keycloak sessions, user bearer and refresh credentials, Gameplay's machine credential, player identities and profile data, picture bytes and metadata, lobby rosters, private question snapshots, match state, results, and notification state. Browser input and API request data are untrusted. The configured Keycloak realm supplies trusted signed claims after each API validates the token. Each service controls access to its own data and accepts other services' requests only through its HTTP boundary.

| Boundary | Data and trust decision |
| --- | --- |
| Browser A and Browser B → Keycloak | Each device runs its own public-client authorization-code flow with PKCE S256. Keycloak owns sign-in and issues credentials to the requesting device. The browser adapter holds credentials in memory. Login may store a match-return ID in session storage, which the API still treats as untrusted input. |
| Browsers → six API hosts | Public-client tokens travel in an Authorization bearer header on protected calls. Identity, Statistics, QuestionBank, Lobby, Gameplay and Notification each validate their own audience and required scope and actor. A caller-relative UI guard provides navigation only. Each service enforces claim-derived ownership or resource membership as specified for the route. |
| Gameplay → Keycloak → four destination APIs | Gameplay authenticates server-side with the confidential client and requests a token scoped to one destination. It caches machine tokens per scope. Each destination validates its own audience, scope and the machine actor. Browser credentials stay outside this flow. |
| APIs → owned stores | Each service owns persistence for its domain. Identity resolves `/api/users/me` from validated issuer and subject. Statistics and Notification also partition user data by issuer and subject. Lobby and Gameplay store only opaque subjects. They rely on a one-issuer-per-store deployment rule with no runtime guard against reusing a store under a different issuer. |
| Identity API → private picture store (#143, #144) → browsers | Identity owns picture rows in its SQL Server database. Its API selects the current profile from validated claims, validates an upload before storage and returns an authorized download through the API. Each device displays downloaded bytes through its own local object URL. |
| Runtime configuration → hosts and CI/deployment | Authority, client IDs, audiences, CORS origins, dependency addresses, database credentials and the Gameplay client secret affect trust decisions. Credential values belong in environment-specific secret storage. Startup, request and error logging must avoid exposing secrets and tokens. |

### Gameplay service calls

| Destination | Privileged operation | Destination audience and exact scope | Protected data or effect |
| --- | --- | --- | --- |
| Lobby | `GET /internal/lobbies/{joinCode}` | `quizarena-lobby`, `lobbies.verify` | Read the verified host and roster before creating a match. |
| QuestionBank | `POST /internal/question-sets` | `quizarena-questionbank`, `questions.play` | Receive private snapshots for play. Public question responses omit the correct answer. |
| Statistics | `POST /api/results` | `quizarena-statistics`, `results.write` | Deliver results from the Gameplay outbox. Identical replay is idempotent and a conflicting replay is rejected. |
| Notification | `POST /events` | `quizarena-notification`, `events.write` | Deliver recipient events from the Gameplay outbox. Identical replay returns the stored event and a conflicting replay is rejected. |

These routes require a valid bearer token with the destination audience, exact scope, signed `azp=quizarena-gameplay`, signed `qa_actor=machine`, and a nonblank subject issued by the configured realm. ### Two independent device sessions

1. A and B complete sign-in separately for the same player. Each device holds its own access and refresh credentials. The APIs resolve the same player from the validated identity. The profile is shared through Identity persistence, while authentication state is local to each device and its Keycloak session.
2. Each device refreshes its own token as needed. The adapter refreshes before sending a protected request when its token has less than 30 seconds of remaining validity. The realm configures a 300-second access-token lifetime, 30-minute SSO idle limit, 10-hour SSO maximum, and refresh-token rotation with zero reuse. On refresh failure or a provider logout notification, the client invalidates its local session, aborts active requests and clears the adapter credentials.
3. Under SEC-08/09, when A replaces a picture, a later authorized profile read on B can observe the new version and fetch the current picture. The contract provides no push synchronization between devices. On sign-out A clears local session state immediately and attempts to end its Keycloak session through the logout redirect. SEC-09 also requires A to clear profile and picture state and revoke its local object URL. B's session should continue independently. #151 sign-out tests and the #160 journey (fixed in #163) are merged. A live journey run on `46f847b` plus #163 passed 17/17 ([#147 run](https://github.com/JimRashed/Web-3-Final-Project/issues/147#issuecomment-7092450545)): independent sessions, B seeing A's upload and replacement, and private headers. Two-device sign-out was not covered by that run or by the journey script ([#160 review](https://github.com/JimRashed/Web-3-Final-Project/pull/160#pullrequestreview-6016902334), [#163 review](https://github.com/JimRashed/Web-3-Final-Project/pull/163#pullrequestreview-6016944462)); #147 was closed with this gap recorded. It was **verified live on `14ac63e`** on 2026-11-24 ([live run](../milestone4/validation-results.md#live-run-main-at-14ac63e), 23/23 PASS): after A signed out, A made no further picture requests, its Keycloak SSO session ended and an unauthenticated read returned 401, while B stayed signed in and fetched the current picture. A's already issued access token was still accepted until expiry (residual below).

## Residual risks and design decisions

- **Token reach and lifetime (SEC-09, SEC-12).** A browser token carries six audiences by design and can authorize matching user routes subject to ownership checks. An issued access token may remain valid after local logout for its remaining lifetime, up to 300 seconds plus 30 seconds of clock skew. The APIs have no access-token revocation list. Keycloak unavailability or a failed redirect can leave the provider session active after local cleanup. Independent devices were verified live on `14ac63e` ([live run](../milestone4/validation-results.md#live-run-main-at-14ac63e)); that run observed this residual: A's issued access token was still accepted (200) after sign-out with about 291 s remaining.
- **Realm and store assumptions (DR-1, DR-5).** Machine identity relies on the configured realm's signed actor and client claims rather than an API subject allowlist. Treat a realm or machine credential compromise as a loss of this boundary. Lobby and Gameplay have no runtime guard against attaching a store populated under another issuer. Deployment configuration must keep each store tied to one issuer. An issuer change requires new empty stores or an explicit identity migration. Track the deployment configuration in [#138](https://github.com/JimRashed/Web-3-Final-Project/issues/138) and reconcile it in [#148](https://github.com/JimRashed/Web-3-Final-Project/issues/148). Existing match and lobby authorization can disclose resource existence through documented 404/403 differences without returning protected resource details. [Authorization matrix](authorization-matrix.md) · [#146](https://github.com/JimRashed/Web-3-Final-Project/issues/146)
- **Picture content and resource limits (SEC-02).** Header validation and the byte cap limit the accepted input, while pixel dimensions, decode cost, embedded metadata and slow uploads retain residual risk. This design defers pixel limits and re-encoding, so metadata such as EXIF location may persist. The format check validates the signature and the first structural chunk only (PNG IHDR, the JPEG frame header including its component count and length, the first WebP chunk), with no CRC, dimension or decode check, so a file with a valid header and a garbage body can be stored. It is served only with its validated type and `nosniff`, so at worst it renders as a broken image. Review these open design questions with the picture implementation. [#144](https://github.com/JimRashed/Web-3-Final-Project/issues/144)
- **Temporary links (SEC-08).** No server-issued temporary, public or signed picture links are in this design, so issuance and link expiry policies do not apply. The API checks authorization on every bearer GET. The browser object URL is a local rendering handle whose lifecycle is governed by explicit revocation. [#144](https://github.com/JimRashed/Web-3-Final-Project/issues/144) · [#145](https://github.com/JimRashed/Web-3-Final-Project/issues/145)
- **Storage availability (DR-3, DR-8).** For Identity, the picture paths and `/me` now map transient storage failures to 503 (#143, #144; [#154](https://github.com/JimRashed/Web-3-Final-Project/pull/154), [#159](https://github.com/JimRashed/Web-3-Final-Project/pull/159)), closing DR-3 for Identity. Statistics, Gameplay's own database and Notification still have equivalent contract gaps (DR-8), with no implementation owner assigned. A remaining Identity low: Kestrel `BadHttpRequestException` maps to 500 on picture routes (#159 review). [Discrepancy register](security-decisions.md#discrepancy-register) · [#143](https://github.com/JimRashed/Web-3-Final-Project/issues/143) · [#148](https://github.com/JimRashed/Web-3-Final-Project/issues/148)
- **Deployment configuration (SEC-10).** The deployment target and corresponding secret store remain open. The [configuration review in PR #153](https://github.com/JimRashed/Web-3-Final-Project/pull/153) records residual exposure through debug or sensitive-data logging (R3) and through connection or host details in exception logs (R1/R2). PR #153 merged on 2026-11-22; these residuals remain after the #138 controls, and the deployment secret store is still undecided. Reconciled in [#148](https://github.com/JimRashed/Web-3-Final-Project/issues/148). [#138](https://github.com/JimRashed/Web-3-Final-Project/issues/138)
