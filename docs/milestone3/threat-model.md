# QuizArena threat model

This model covers [SEC-A3 (#139)](https://github.com/JimRashed/Web-3-Final-Project/issues/139). It uses the issue's historical baseline `c8dcc78` and reviews the integration base `feature/milestone-4-security-and-cross-device-profiles` at `deef7c0`, including the merged token and route authorization work. The [SEC-A1 decisions](security-decisions.md) and [authorization matrix](authorization-matrix.md) were merged through [PR #149](https://github.com/JimRashed/Web-3-Final-Project/pull/149) and issue #137 is closed. The decisions document still records team approval as pending. Picture controls below describe that merged design, with implementation and live evidence tracked separately.

## Assets and trust boundaries

The assets are Keycloak sessions, user bearer and refresh credentials, Gameplay's machine credential, player identities and profile data, picture bytes and metadata, lobby rosters, private question snapshots, match state, results, and notification state. Browser input and API request data are untrusted. The configured Keycloak realm supplies trusted signed claims after each API validates the token. Each service controls access to its own data and accepts other services' requests only through its HTTP boundary.

| Boundary | Data and trust decision |
| --- | --- |
| Browser A and Browser B → Keycloak | Each device runs its own public-client authorization-code flow with PKCE S256. Keycloak owns sign-in and issues credentials to the requesting device. The browser adapter holds credentials in memory. Login may store a match-return ID in session storage, which the API still treats as untrusted input. |
| Browsers → six API hosts | Public-client tokens travel in an Authorization bearer header on protected calls. Identity, Statistics, QuestionBank, Lobby, Gameplay and Notification each validate their own audience and required scope and actor. A caller-relative UI guard provides navigation only. Each service enforces claim-derived ownership or resource membership as specified for the route. |
| Gameplay → Keycloak → four destination APIs | Gameplay authenticates server-side with the confidential client and requests a token scoped to one destination. It caches machine tokens per scope. Each destination validates its own audience, scope and the machine actor. Browser credentials stay outside this flow. |
| APIs → owned stores | Each service owns persistence for its domain. Identity resolves `/api/users/me` from validated issuer and subject. Statistics and Notification also partition user data by issuer and subject. Lobby and Gameplay use opaque subjects inside stores dedicated to the configured issuer. |
| Identity API → proposed private picture store → browsers | Identity owns picture rows in its SQL Server database. Its API selects the current profile from validated claims, validates an upload before storage and returns an authorized download through the API. Each device displays downloaded bytes through its own local object URL. |
| Runtime configuration → hosts and CI/deployment | Authority, client IDs, audiences, CORS origins, dependency addresses, database credentials and the Gameplay client secret affect trust decisions. Credential values belong in environment-specific secret storage. Startup, request and error logging must avoid exposing secrets and tokens. |

### Gameplay service calls

| Destination | Privileged operation | Destination audience and exact scope | Protected data or effect |
| --- | --- | --- | --- |
| Lobby | `GET /internal/lobbies/{joinCode}` | `quizarena-lobby`, `lobbies.verify` | Read the verified host and roster before creating a match. |
| QuestionBank | `POST /internal/question-sets` | `quizarena-questionbank`, `questions.play` | Receive private snapshots for play. Public question responses omit the correct answer. |
| Statistics | `POST /api/results` | `quizarena-statistics`, `results.write` | Deliver results from the Gameplay outbox. Identical replay is idempotent and a conflicting replay is rejected. |
| Notification | `POST /events` | `quizarena-notification`, `events.write` | Deliver recipient events from the Gameplay outbox. Identical replay returns the stored event and a conflicting replay is rejected. |

These routes require a valid bearer token with the destination audience, exact scope, signed `azp=quizarena-gameplay`, signed `qa_actor=machine`, and a nonblank subject issued by the configured realm. [Machine token provider](../../src/QuizArena.Gameplay.Api/Services/MachineTokens.cs) · [Delivery worker](../../src/QuizArena.Gameplay.Api/Services/Outbox/DeliveryWorker.cs) · [Delivery channels](../../src/QuizArena.Gameplay.Api/Services/Outbox/DeliveryChannels.cs)

### Two independent device sessions

1. A and B complete sign-in separately for the same player. Each device holds its own access and refresh credentials. The APIs resolve the same player from the validated identity. The profile is shared through Identity persistence, while authentication state is local to each device and its Keycloak session.
2. Each device refreshes its own token as needed. The adapter refreshes before sending a protected request when its token has less than 30 seconds of remaining validity. The realm configures a 300-second access-token lifetime, 30-minute SSO idle limit, 10-hour SSO maximum, and refresh-token rotation with zero reuse. On refresh failure or a provider logout notification, the client invalidates its local session, aborts active requests and clears the adapter credentials.
3. Under SEC-08/09, when A replaces a picture, a later authorized profile read on B can observe the new version and fetch the current picture. The proposed contract provides no push synchronization between devices. On sign-out A clears local session state immediately and attempts to end its Keycloak session through the logout redirect. SEC-09 also requires A to clear profile and picture state and revoke its local object URL. B's session should continue independently. The complete live behavior is tracked in [#147](https://github.com/JimRashed/Web-3-Final-Project/issues/147).

## Threat and mitigation trace

| Threat | Boundary | Mitigation and delivery state | Implementation or verification |
| --- | --- | --- | --- |
| An API accepts a token for another issuer, audience or purpose, or accepts an expired or invalidly signed token. | Keycloak → APIs | Merged. All six hosts require the configured issuer and exact host audience, issuer metadata signing keys and RS256, an expiry within 30 seconds of skew, and bearer token type. Authentication fails before authorization. | [#140 token validation](https://github.com/JimRashed/Web-3-Final-Project/issues/140), [#142 CI matrix](https://github.com/JimRashed/Web-3-Final-Project/issues/142) |
| Browser credentials are exposed through application persistence, URLs or logs. | Browser → Keycloak and APIs | Browser baseline keeps tokens in adapter memory, uses PKCE S256 and sends API tokens as bearer headers. The browser token still spans six audiences. The picture design keeps the bearer outside the image URL. Configuration and log review are tracked separately. | [#138 secrets and configuration](https://github.com/JimRashed/Web-3-Final-Project/issues/138), [#140 audience validation](https://github.com/JimRashed/Web-3-Final-Project/issues/140), [#145 picture rendering](https://github.com/JimRashed/Web-3-Final-Project/issues/145) |
| A user reaches a machine route or machine credentials reach a user route. | Browsers or Gameplay → APIs | Merged. Named route policies require exact scope membership, signed client and actor claims, and a nonblank subject. Gameplay requests a destination-specific scope and sends its own bearer token. The receiving service authenticates and authorizes independently. | [#141 route policies](https://github.com/JimRashed/Web-3-Final-Project/issues/141), [#142 CI matrix](https://github.com/JimRashed/Web-3-Final-Project/issues/142), [#146 service contract verification](https://github.com/JimRashed/Web-3-Final-Project/issues/146) |
| A caller reads or modifies another player's data, acts as another lobby host, or accesses a match they did not join. | Browser → API → owned store | Merged for shipped routes. Resolve identity from validated claims. Enforce self-only access on profile, stats, history, events and preferences as applicable. Verify the host for lobby lock and match creation and the participant for match reads and answers. Proposed picture operations reuse claim-based profile ownership. | [#141 ownership](https://github.com/JimRashed/Web-3-Final-Project/issues/141), [#143 private persistence](https://github.com/JimRashed/Web-3-Final-Project/issues/143), [#144 owner-only picture API](https://github.com/JimRashed/Web-3-Final-Project/issues/144) |
| Gameplay leaks machine credentials or private roster and answer data, or repeated delivery changes results or events. | Gameplay → Keycloak and destination APIs | Machine credentials stay on the server, the destinations check the dedicated policy, and published question views omit answers. Statistics and Notification distinguish identical and conflicting replays. Integrated service verification is pending. | [#138 configuration](https://github.com/JimRashed/Web-3-Final-Project/issues/138), [#141 actor policies](https://github.com/JimRashed/Web-3-Final-Project/issues/141), [#146 service contract verification](https://github.com/JimRashed/Web-3-Final-Project/issues/146) |
| Unsafe runtime settings or logs expose secrets or weaken issuer and origin boundaries. | Configuration → hosts and CI/deployment | The baseline pins issuer and audience and uses configured CORS origins. SEC-10 specifies ignored local configuration, CI secrets, and secret-free logs. Environment-specific validation and review are tracked in #138. Deployment secret storage remains open. | [#138 environment controls](https://github.com/JimRashed/Web-3-Final-Project/issues/138), [#140 issuer pin](https://github.com/JimRashed/Web-3-Final-Project/issues/140) |
| An oversized, unsupported or malformed image reaches storage or decoding. | Browser → Identity picture PUT and browser rendering | Proposed. Allow only PNG, JPEG or WebP, verify type against the format header, reject malformed bodies and enforce 2 MiB while reading. Validate before persistence. Delivery uses the stored validated content type and `nosniff`. | [#144 upload validation and delivery](https://github.com/JimRashed/Web-3-Final-Project/issues/144), [#145 client handling](https://github.com/JimRashed/Web-3-Final-Project/issues/145) |
| A failed or concurrent picture replacement loses the previous picture or returns partial content. | Identity API → private SQL store → devices | Proposed. Store one picture per profile. Validate before an atomic replacement, use SQL concurrency checks, increment version only after successful replacement and return 409 to a losing writer. Return 503 upon storage failure and preserve the previous committed picture on a failed write. The client can reload profile state after a conflict. | [#143 storage](https://github.com/JimRashed/Web-3-Final-Project/issues/143), [#144 API failure behavior](https://github.com/JimRashed/Web-3-Final-Project/issues/144), [#145 client handling](https://github.com/JimRashed/Web-3-Final-Project/issues/145), [#147 cross-device evidence](https://github.com/JimRashed/Web-3-Final-Project/issues/147) |
| Picture bytes or addressing information escape private delivery, shared caching, or a signed-out browser. | Private SQL store → Identity API → browser | Proposed. Use claim-derived owner-only GET, omit storage paths and URLs from the profile, send `Cache-Control: private, no-store` and `nosniff`, and revoke client object URLs on replacement, sign-out and unmount. | [#143 private persistence](https://github.com/JimRashed/Web-3-Final-Project/issues/143), [#144 private response](https://github.com/JimRashed/Web-3-Final-Project/issues/144), [#145 object URLs](https://github.com/JimRashed/Web-3-Final-Project/issues/145), [#147 cross-device evidence](https://github.com/JimRashed/Web-3-Final-Project/issues/147) |
| A stale session continues issuing requests after logout, or signing out one device disrupts another. | Browser A and B → Keycloak and API | Current client invalidates local state and aborts requests immediately and its refresh generation check prevents reactivating a cleared session. Ending A's Keycloak session requires completing the provider redirect. Proposed picture cleanup and verification of B's continued session are tracked separately. | [#145 picture and session UI](https://github.com/JimRashed/Web-3-Final-Project/issues/145), [#147 live device verification](https://github.com/JimRashed/Web-3-Final-Project/issues/147) |

## Residual risks and design decisions

- **Token reach and lifetime (SEC-09, SEC-12).** A browser token carries six audiences by design and can authorize matching user routes subject to ownership checks. An issued access token may remain valid after local logout for its remaining lifetime, up to 300 seconds plus 30 seconds of clock skew. The APIs have no access-token revocation list. Keycloak unavailability or a failed redirect can leave the provider session active after local cleanup. Verify independent devices in [#147](https://github.com/JimRashed/Web-3-Final-Project/issues/147).
- **Realm and store assumptions (DR-1, DR-5).** Machine identity relies on the configured realm's signed actor and client claims rather than an API subject allowlist. Treat a realm or machine credential compromise as a loss of this boundary. If the issuer changes, Lobby and Gameplay require new empty stores or an explicit identity migration. Existing match and lobby authorization can disclose resource existence through documented 404/403 differences without returning protected resource details. [Authorization matrix](authorization-matrix.md) · [#146](https://github.com/JimRashed/Web-3-Final-Project/issues/146)
- **Picture content and resource limits (SEC-02).** Header validation and the byte cap limit the accepted input, while pixel dimensions, decode cost, embedded metadata and slow uploads retain residual risk. This design defers pixel limits and re-encoding, so metadata such as EXIF location may persist. Review these open design questions with the picture implementation. [#144](https://github.com/JimRashed/Web-3-Final-Project/issues/144)
- **Temporary links (SEC-08).** No server-issued temporary, public or signed picture links are in this design, so issuance and link expiry policies do not apply. The API checks authorization on every bearer GET. The browser object URL is a local rendering handle whose lifecycle is governed by explicit revocation. [#144](https://github.com/JimRashed/Web-3-Final-Project/issues/144) · [#145](https://github.com/JimRashed/Web-3-Final-Project/issues/145)
- **Storage availability (DR-3, DR-8).** Identity's current error mapping can return 500 where the contract declares 503. Identity picture persistence tracks the Identity gap in #143. Statistics, Gameplay's own database and Notification still have equivalent contract gaps. DR-8 has no implementation owner assigned. D3 can record the remaining discrepancy during reconciliation. [Discrepancy register](security-decisions.md#discrepancy-register) · [#143](https://github.com/JimRashed/Web-3-Final-Project/issues/143) · [#148](https://github.com/JimRashed/Web-3-Final-Project/issues/148)
- **Deployment configuration (SEC-10).** The deployment target and corresponding secret store remain open. Validate the environment configuration before treating the deployed trust boundaries as verified. [#138](https://github.com/JimRashed/Web-3-Final-Project/issues/138)
