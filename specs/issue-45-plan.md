## Ordered implementation steps

1. **Define Data rows and mappings.** Use nonempty Guid primary keys; `ActiveLobbies` has required six-character non-Unicode JoinCode, required Unicode HostId (max 200), required status, a SQL Server `rowversion` concurrency token and persistence-only `long WriteRevision`. `LobbyPlayers` has Guid key, required LobbyId FK and Unicode PlayerId (max 200). Use `Latin1_General_100_BIN2` for HostId and PlayerId so case-distinct opaque subjects agree with Domain ordinal identity; use strict binary JoinCode collation too. Name indexes `IX_ActiveLobbies_JoinCode` and `IX_LobbyPlayers_LobbyId_PlayerId`, both unique. Configure required parent relationship with `DeleteBehavior.Cascade`. Use separate `IEntityTypeConfiguration<T>` classes; do not map mutable EF setters into Domain. Do not put capacity or host authorization logic in configurations/triggers. Completion: owned model contains only these two business tables and the required indexes/FK/concurrency metadata; Domain and legacy files are unchanged.
2. **Define the #46 persistence port.** All methods accept `CancellationToken = default`, return Domain `ActiveLobby` only and keep EF rows/tokens private to Data. Specify `Task<ActiveLobby> CreateAsync(string hostId, CancellationToken cancellationToken = default)`, `Task<ActiveLobby?> GetByJoinCodeAsync(string joinCode, CancellationToken cancellationToken = default)`, `Task<ActiveLobby?> JoinAsync(string joinCode, string playerId, CancellationToken cancellationToken = default)` and `Task<ActiveLobby?> SaveAsync(string joinCode, Func<ActiveLobby, bool> mutation, CancellationToken cancellationToken = default)`. A missing lobby returns null for later Api 404 mapping. `JoinAsync` calls the common save engine with `lobby => lobby.Join(playerId)`; #46 locks with `lobby => lobby.Lock(trustedSubject)`. Save's callback must be pure, repeatable, synchronous and return whether Domain changed: it can execute again after a conflict, so never perform network calls, notifications or other external effects in it. Domain exceptions pass through unchanged for later 400/403/409 mapping. This is a persistence retry boundary around a supplied Domain decision, not business logic implemented in SQL. Completion: #46 can mock one port and orchestrate all four workflows without accessing context, rows or concurrency tokens.
3. **Implement checked mapping and reads.** Validate supplied codes using the existing Domain validator before querying. Read by code with `AsNoTracking`, eagerly loading the complete membership in one aggregate read; no tracked row or navigation escapes. Map each membership with `LobbyPlayer.Rehydrate`, then the root with `ActiveLobby.Rehydrate`; corrupt persisted data must fail validation rather than weakening Domain or constructing unchecked objects. Order membership consistently when returning data without assuming a database row order. Forward cancellation through context creation/query/save/transaction operations and throw cancellation before entering work. Completion: create/read across independently disposed contexts preserves IDs, host, case-sensitive subjects, membership and Open/Locked state; read-only tracking remains empty.
4. **Implement bounded create and code collision recovery.** Inject `IJoinCodeSource`; default source calls the existing BCL Domain generator. Each attempt creates a valid Domain aggregate with host first, maps both rows and commits them atomically. Allow at most five total candidates/insert attempts. Retry only SQL Server 2601/2627 errors attributable to the exact owned JoinCode index; inspect the named constraint/index as well as SQL error number, not every `DbUpdateException` or every uniqueness violation. Dispose/rollback the failed attempt context before a new candidate; do not retain failed host rows. Unrelated PK/member/foreign-key/length/connection errors and invalid candidates propagate, and cancellation never becomes a collision retry. On exhaustion throw a typed persistence failure with a fixed safe reason, not a fabricated domain capacity conflict. Completion: deterministic source sequence collision/collision/free succeeds with one new valid lobby; all-collision source stops after five attempts without partial rows.
5. **Implement atomic mutation and optimistic retry.** Each attempt gets a fresh context from `IDbContextFactory<LobbyDbContext>`, loads the tracked row plus all players, checks Domain rehydration and invokes the supplied Domain operation. Unchanged results are returned without duplicate insertion or a needless mutation; Domain still checks Locked before duplicate joins and authorization before repeated lock. For any changed membership or status, increment `WriteRevision` so EF necessarily updates the parent with its original rowversion. Persist parent version check/update and membership insert in the same transaction: a failed parent concurrency check must roll back the whole attempted graph. Never rely on a member insert to change parent rowversion automatically. Never offer a stale-aggregate save overload that bypasses this engine. Retry at most three total mutation attempts after `DbUpdateConcurrencyException`; dispose the failed graph, reload and rerun the Domain decision. A narrowly classified owned membership unique-key race may also retry through this same bounded reload path; unrelated unique violations must not be swallowed. The reloaded domain may return an idempotent existing member or throw full/Locked/forbidden, with no stale decision reused. Return a typed persistence failure after genuine retry exhaustion; do not loop forever or misreport it as ordinary domain conflict. Completion: two distinct simultaneous last-slot requests can leave only two members total, duplicate concurrent joins produce one membership, and joins/locks have an outcome consistent with a valid serial ordering.
6. **Generate and inspect the owned migration.** Run pinned EF migration generation after model/repository code compiles. Preserve both existing InitialCreate artifacts; inspect generated Up/Down/Designer/snapshot for only the owned two-table schema, indexes, lengths, binary collations, cascade and SQL rowversion. No `EnsureCreated`, startup migration call, peer schema, legacy schema or destructive data transfer is introduced. Completion: migrations apply in order to a fresh disposable database, no pending model changes remain, and reads succeed through a new context.
7. **Add and run the tests below.** Use the existing owned IntegrationTests project and descriptive scenarios, no dispatcher-specific test tree. Exercise actual SQL Server relational behavior, not EF InMemory or SQLite substitutes. Use controlled interceptors/barriers only in tests to force the competing requests to observe the same initial state; never use sleeps to hope for a race. Capture focused tests and full regression, then pass actual results to Testing, Validate and read-only Code Review. Completion: every acceptance row has executable evidence and the concurrency tests prove persisted outcomes through independent final contexts.

## Testing strategy

Use xUnit and FluentAssertions with Arrange/Act/Assert. SQL Server is required because unique collation, rowversion, transaction rollback and concurrent writes are this task's behavior. The existing `QUIZARENA_TEST_SQLSERVER` server-only connection setting takes precedence over default `(localdb)\MSSQLLocalDB`; never print credentials. The test helper assigns a unique `QuizArenaLobby_<scenario>_<guid>` database, migrates it, creates independent context/factory instances and drops only that exact test database in asynchronous cleanup, including on failure. No production/development database is reused. This local helper follows P04 and does not claim to complete shared fixture issue #24.

- Migration/schema: existing lineage plus new migration applies; no pending migrations/model differences; only owned business tables; required fields, lengths and indexes exist; persisted create/join/lock can be read after disposing the original contexts. Invalid Domain rehydration from deliberately corrupted stored rows fails rather than silently returning an invalid aggregate.
- Constraints: real duplicate code fails; duplicate exact subject in one lobby fails; same subject across lobbies succeeds; case-distinct subjects coexist; missing parent FK fails; parent deletion removes memberships; direct stale parent version save throws `DbUpdateConcurrencyException`; a repository join updates parent rowversion even when status does not change.
- Repository behavior: host-first create, strict invalid-code rejection, missing read/join/save null, second join, Open duplicate idempotency with stable membership ID, full/Locked rejection, host-only two-player lock, repeated host lock and nonhost forbidden even after Locked. Verify unchanged state after rejections through fresh contexts.
- Collision tests: seed a known code, inject candidate sequence returning collisions then a free code, assert bounded calls and one durable aggregate. All collisions exhaust exactly five attempts. Test unrelated unique/SQL failures are not retried as code collisions. Cancellation before entry and during a blocked I/O/retry boundary propagates `OperationCanceledException` without another attempt or partial commit.
- Concurrency tests: barrier/interceptor coordinates two separate repository/context instances after the same version has been read. Distinct last-slot joiners yield one joined subject and one Domain full conflict after reload; final roster count is two. Same-subject last-slot joiners converge to one membership and two idempotent successful results. Exercise a join/lock overlap (including one-member join versus lock and full-roster existing-member join versus host lock) with serially valid outcomes, no new member after lock, no rollback of a successful lock, and stable two-member Locked persistence. Force repeated parent-version changes deterministically to exercise three-attempt exhaustion and cleanup. Use bounded barrier timeouts/finally release so a failed assertion cannot hang the suite.
- Isolation: tests never depend on execution order or external service tables. Fresh final readers verify committed results, not merely tracked objects. Do not add packages or mock away the relational assertions. Existing Domain tests continue to cover pure rules; #46 adds mocked application orchestration separately.
